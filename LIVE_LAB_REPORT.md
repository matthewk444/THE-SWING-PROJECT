# Connect live swings to trustworthy comparisons

Research and implementation report for Matthew Kim • October 23, 2026

**THE SWING PROJECT now has a browser-based Live Swing Lab implementation for camera guidance, short rep capture, movement review and experimental reference matching.** This extends the original local Streamlit video-review prototype into a more immediate training workflow. The matching system compares actual extracted movement sequences supplied by the user; it does not invent MLB profiles or infer professional ability. Research found one explicitly licensed Dustin Pedroia video candidate, but no curated, usable multi-player MLB bank has been acquired. Nine JavaScript tests and seven Python tests pass, and isolated headless Chrome integration checks passed with the actual pose model and synthetic camera/video inputs. Physical-camera and real-hitter performance remain unvalidated. The next meaningful milestone is a tested capture experience plus a small, attributable reference collection with quality-reviewed poses. Improving hitter outcomes remains a separate research question from making the interface work.

## Live feedback works best before and after the rep

The implemented interface offers an explicit camera-start button, a skeleton overlay, full-body tracking cues, projected lead-knee angle, and a three-second countdown followed by a four-second capture window. This captures pose samples rather than recording video. Afterward, the user can inspect skeleton samples, trim the movement window, see tracking coverage and observed knee-angle range, and export the rep. An alternate file workflow analyzes up to eight playback seconds at 20 samples per playback second. **Automatic swing detection, contact identification and synchronized source-video replay are not implemented.** The review canvas shows extracted skeletons; the uploaded source remains available separately in its video player.

MediaPipe's web API processes video frames synchronously, and Google recommends workers to avoid blocking the interface. The implementation uses a worker with local package, WASM and model assets, GPU initialization with a CPU retry, and one inference request in flight. It releases the camera and invalidates pending work when stopped or when the tab becomes hidden. The server binds to loopback rather than exposing the project directory across a network. Camera access requires browser permission and a secure context; localhost qualifies, while another device's plain-HTTP LAN address generally does not. ([MediaPipe web guide](https://developers.google.com/edge/mediapipe/solutions/vision/pose_landmarker/web_js), [MDN camera access](https://developer.mozilla.org/en-US/docs/Web/API/MediaDevices/getUserMedia))

The camera requests an ideal 60 fps, but that is a preference, not a measured capture guarantee. Live analysis is throttled and skips busy or duplicate frames; the interface separates camera settings, completed analysis rate and worker inference time. None is a camera-to-screen latency measurement. Source/playback time also differs from original acquisition time in edited slow-motion clips. More detailed dropped-frame and end-to-end latency instrumentation remains future work. Browser video callbacks themselves have display-rate and scheduling limits, reinforcing the need to measure the supported device instead of advertising an assumed real-time rate. ([MDN video frame callbacks](https://developer.mozilla.org/en-US/docs/Web/API/HTMLVideoElement/requestVideoFrameCallback))

The coaching design should remain quiet during the explosive movement. Use live cues to improve framing, then give one evidence-linked observation and one coach-selected experiment between reps. This is a proposed workflow, not proof of improved hitting. The current live knee angle is descriptive, and its range is not an ideal target.

## Resemblance is a reference ranking, not a percentage

The implemented feature vector contains seven projected descriptors: lead/trail knee angles, lead/trail elbow angles, normalized stance width, and horizontal/vertical hand position relative to the hips. Geometry uses pixel coordinates, torso scale and explicit lead/trail mapping. Declared pitcher direction canonicalizes horizontal hand position. Users must supply **unmirrored footage from a fixed side view**, and comparisons require the same batting side, open/back camera view and practice type. These metadata filters reduce obvious mismatch; they do not remove perspective distortion or verify the user's labels.

Eligible sequences are resampled to 32 time-normalized samples and compared using band-constrained dynamic time warping, or DTW. The implementation minimizes accumulated frame cost and displays that path's cost divided by path length. It shows lower-is-closer distances, source notes, a knee-trace overlay across normalized time and the largest feature differences from simple time-normalized comparison. Those feature differences are not a decomposition of the DTW alignment. DTW can align unequal-speed movements, but aggressive alignment can conceal meaningful timing differences. The current method has no manual phase anchors or displayed alignment path; those are next-stage improvements. ([DTW guide](https://tslearn.readthedocs.io/en/stable/user_guide/dtw.html), [Baseball motion-matching research](https://www.ams.giti.waseda.ac.jp/data/pdf-files/2022_GCCE_osawa.pdf))

Engineering gates require at least 12 usable samples, 70% coverage, half a second of source/playback span, no sample or accepted-tracking gap above 350 ms, and detectable feature movement. These are conservative implementation choices awaiting evaluation, **not scientifically validated accuracy thresholds**. The current capture is excluded from matching itself. An empty or incompatible library produces no ranking; a nonempty eligible library can still return weak matches because no calibrated out-of-distribution distance threshold exists. The product therefore says “closest among compatible reference clips,” not “92% like Ohtani.” Similar movement does not establish similar skill, power or future performance.

Body landmarks do not include the bat. Statcast attack angle and swing-path tilt are defined from bat movement around impact, so those quantities cannot be inferred from this seven-feature body comparison. A future player-information panel could show separately sourced statistics without treating them as the matching signal. ([Statcast definitions](https://baseballsavant.mlb.com/leaderboard/bat-tracking/swing-path-attack-angle))

## A legitimate MLB bank requires actual clips and provenance

The bounded search identified **Dustin PedroiaBatting.ogv**, a 6.72-second, 1920×1080 Wikimedia Commons video credited to Elgaard, dated April 18, 2014, under CC BY-SA 3.0. It is a candidate for a real, named demonstration. It has not been imported or pose-reviewed, so full-body visibility, viewpoint compatibility and useful swing coverage remain unknown. Its license requires attribution, license linkage, change notices and share-alike handling where applicable. One clip supports comparison to that clip; it does not establish the closest player across MLB. ([Pedroia file and license](https://commons.wikimedia.org/wiki/File:Dustin_PedroiaBatting.ogv))

MLB-YouTube supplies activity annotations, not a cleared commercial player-reference gallery. OpenBiomechanics uses anonymized athletes and restricted data terms, so it cannot supply named MLB templates. Public access and useful labels do not automatically establish footage redistribution rights. ([MLB-YouTube](https://github.com/piergiaj/mlb-youtube), [OpenBiomechanics datasheet](https://github.com/drivelineresearch/openbiomechanics/blob/main/DATASHEET.md), [OBP data terms](https://github.com/drivelineresearch/openbiomechanics/blob/main/LICENSE-DATA.md))

The current library accepts up to 12 named references with capture metadata and a required source/permission note. Names are user-entered and unverified. References persist in browser localStorage as extracted features, timestamps, metadata and source notes; original video is not saved or uploaded. Rep exports can include pose landmarks. Model/package assets are served locally, but the broader MediaPipe documentation includes performance/utilization telemetry language, so local processing should not be described as a guarantee of zero network activity. ([MediaPipe package notice](https://pypi.org/project/mediapipe/))

The next reference schema should separate source URL, creator, license, retrieval date, file hash, player identity evidence, acquisition/playback timing, model version, transformations and event boundaries. A rights-cleared clip still needs independent quality labels. Store whether the full swing is visible, relevant joints track, the camera moves, and the declared view/drill is trustworthy. Reject unsuitable clips even when their player name is attractive.

## Existing products set a higher bar than skeleton overlays

Onform advertises automatic swing capture, up to four camera angles, slow motion, drawings, commentary and side-by-side/overlay comparison. Its live-drawing feature explicitly supports setup analysis before recording. SwingAI advertises short-clip analysis, one focus/drill and coach overrides, but its inspected page retains a Spring 2026 availability statement; this review did not verify actual availability or efficacy. Reboot Motion offers organizational biomechanics processing and comparison APIs, with authenticated customer data rather than an open MLB reference bank. These are vendor-described capabilities, not independently tested results. ([Onform baseball](https://onform.com/sports/baseball/), [Onform live drawing](https://support.onform.com/article/110-live-drawing-helps-analyze-setup-form-before-recording), [SwingAI](https://getswingai.com/), [Reboot comparison API](https://docs.rebootmotion.com/tutorials/create-requested-analyses))

The proposed distinction is a transparent loop: capture comparable reps, inspect the evidence, choose one experiment, then compare both movement and independent contact quality. Personal baselines should be the default, with MLB resemblance as optional exploration. The reference library should expose provenance and uncertainty instead of turning every swing into a fault list or a professional-looking grade. Whether this distinction creates demand needs coach interviews and repeated use, not assumptions based on competitor websites.

## The next sprint should establish trustworthy real examples

The source implementation, deterministic tests and research are concrete progress. **Nine JavaScript and seven Python tests pass. Isolated headless Chrome integration checks also passed.** These exercised actual MediaPipe worker inference on a blank frame with zero detected poses; synthetic-camera countdown, capture, insufficient-evidence handling and camera-track cleanup; generated WebM import and decoded-frame inference; reference JSON import, localStorage persistence and removal; and mobile overflow. A module-worker/WASM loading issue was fixed by selecting the module loader through `forVisionTasks(absoluteURL, true)`. Tests cover missing/insufficient/multiple-person tracking, prolonged tracking gaps, no-motion rejection and exclusion of the same capture from its own ranking. Startup inference times varied substantially, so these checks do not establish steady live latency. The isolated browser used synthetic inputs, not Matthew's physical camera or a real hitter. No real-camera benchmark, validated MLB retrieval accuracy or player-development result is claimed. The Live Lab runs at `http://127.0.0.1:8502`; the preserved Streamlit service at port 8501 also passed its health check.

A practical next sprint is approximately one to two weeks after runtime stabilization, assuming one developer and access to a coach. First inspect the Pedroia candidate, preserve its attribution, and decide whether it passes view/pose quality review. Then seek permissioned footage for a small same-view collection, ideally several genuine swings per player; if rights or capture conditions fail, begin with consenting local hitters and personal baselines. A target of three to five named reference players is a collection goal, not an acquired asset or guaranteed schedule. Add structured provenance, manual event anchors, duration comparison and inspectable alignment before expanding the library.

Run a device and failure-case matrix covering camera denial, repeated start/stop, tab backgrounding, missing feet, multiple people, motion blur, different aspect ratios and slow-motion files. Benchmark p50/p95 processing and post-rep response times on the actual Mac. Validate projected measurements against independent manual digitization, then test ranking stability under noise and viewpoint changes with blinded coach judgments. Hold out hitters and sessions. Only after these steps should a larger prospective study ask whether coach-plus-tool improves independent outcomes. A working live display and an interesting resemblance ranking are useful milestones; neither alone proves better hitting.
